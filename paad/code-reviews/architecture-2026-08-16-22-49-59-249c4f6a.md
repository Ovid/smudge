## Important Issues

### [I1] The S3 pending announcement is spoken; its retraction to `""` never is
- **File:** `packages/client/src/hooks/useKeyboardShortcuts.ts:211-224` (retraction at `:218`); live region at `packages/client/src/components/EditorDialogs.tsx:146-148`
- **Bug:** `:211` fires `STRINGS.sidebar.navigatingToChapter(...)` into the polite live region unconditionally at keypress, before any refusal is known. Every refusal routes to `settle(false)` → `deps.setNavAnnouncement("")` at `:218`. The markup is a bare `<div aria-live="polite" className="sr-only">` with **no** `aria-atomic` (the sibling image region at `:152` does set it), and emptying a polite region produces no announcement. The codebase already knows this: the word-count shortcut in this same file (`:166-170`) clears and then re-sets inside `requestAnimationFrame` precisely because a clear alone announces nothing. The inline comment at `:215-217` half-concedes the point ("does not un-speak it") but then claims the clear "stops the live region asserting a navigation that is still in progress" — it does not; nothing reaches the user either way.
- **Impact:** `EditorPage.tsx:767-769` returns `false` on `editorMachine.isLocked()` with **no new banner, by design**. A screen-reader user pressing Ctrl+Shift+Arrow with the editor locked hears "Navigating to Chapter Two…" for a navigation that will never happen, and receives no correction. This is deterministic on a single keypress, and WCAG 2.1 AA is a first-class constraint per CLAUDE.md. The abort/supersede paths (`useChapterCrud.ts:460-461`, `:472`, `:474`) return `false` without raising anything either. Mitigating: the non-dismissible lock banner is already on screen and was announced when the lock fired. The busy-latch path is covered by `actionInfo` (`role="status"`) and the flush-failure path by the save-failed banner — the lock path is the residual.
- **Suggested fix:** In the `!navigated` arm, set an explicit refusal string (a new `STRINGS.sidebar` constant) instead of `""`, reusing the existing 1s clear timer. **Land [S2]'s epoch guard in the same change** — replacing `""` with real copy converts that latent race into a spoken lie.
- **Confidence:** Medium
- **Found by:** Error Handling & Edge Cases (`claude-opus-5[1m]`)

### Adjudicated specialist contradiction

Two specialists reached **opposite** empirical conclusions about ESLint 9 flat-config `files:`
glob resolution, each citing a `--print-config` run. The Verifier reproduced both on the installed
ESLint 9.39.4 and resolved it:

- Under **config-file discovery** (no `--config` flag), the base path is the *config file's*
  directory, so `files: ["packages/client/**/*.{ts,tsx}"]` matches from any cwd.
- Under an explicit **`--config`** (relative *or* absolute), the base path is cwd, and the
  workspace blocks match nothing.

Root `package.json`'s `lint`/`lint:check` scripts use discovery with no `--config`, `Makefile`
just calls those, no per-workspace lint script exists, and there is no IDE config in the repo — so
discovery is the only path this repo uses. A live off-root probe (`cd packages/client && echo
'import express …' | npx eslint --stdin --stdin-filename src/__probe.ts`) made the rule genuinely
fire. The finding claiming S5's fix was incomplete was therefore **dropped as a false positive**,
and its proposed `basePath: REPO_ROOT` change is unnecessary. The surviving finding was narrowed to
comment accuracy only ([S8]), with its sub-claim that `eslint.config.js:10-15` shares the false
premise **rejected** — that comment concerns `packageDir`, and `path.resolve(dir)` at
`eslint-plugin-import/lib/rules/no-extraneous-dependencies.js:70,72` confirms it is correct.
