## Important Issues

### [I1] `image.upload`'s `committedCodes` is inert — the client half of F-12 never fires
- **File:** `packages/client/src/errors/scopes.ts:330`
- **Bug:** `_resolveErrorInternal` sets `possiblyCommitted` **only** inside the
  `typeof byCodeMatch === "string"` branch (`apiErrorMapper.ts:133-145`); the `byStatus`
  branch (`:147-158`) and the `fallback` (`:160-166`) both hard-code it to `false`.
  `image.upload.byCode` (`:339-346`) holds only `PAYLOAD_TOO_LARGE` and `VALIDATION_ERROR`,
  and `byStatus` (`:331-338`) only 413/404 — no 500. The server emits
  `READ_AFTER_INSERT_FAILURE` as a 500 (`images.repository.ts:16`), so the new scope entry
  resolves to `uploadFailedGeneric` with `possiblyCommitted: false`.
- **Impact:** Both consumers that gate on the flag (`ImageGallery.tsx:215-226`,
  `Editor.tsx:366`) stay dark, so the gallery is never refreshed and the user is shown copy
  that explicitly invites a retry — for a row that **is** committed and whose file this
  branch now deliberately keeps on disk (`images.service.ts:109`). Per CLAUDE.md
  §Accepted Architectural Trade-offs F-8 uploads are non-idempotent with no dedup, so the
  retry mints a duplicate row + duplicate blob. The server half of F-12 works; the half the
  user experiences is dead. The sibling `image.updateMetadata` entry (`scopes.ts:455-463`,
  added 2026-08-16) states the rule verbatim — "`committedCodes` only takes effect on a
  byCode match, so both are required" — and every other `committedCodes` site in the
  registry pairs correctly. `image.upload` is the sole exception. No client test covers it.
- **Suggested fix:** Add `READ_AFTER_INSERT_FAILURE: STRINGS.imageGallery.uploadCommittedRefresh`
  to `image.upload.byCode` (the string already exists at `strings.ts:439`), plus a mapper
  test asserting `possiblyCommitted === true`. See also [S7].
- **Confidence:** High
- **Found by:** Logic & Correctness, Error Handling & Edge Cases, Contract & Integration, Security, Spec Compliance (`claude-opus-5[1m]`)

### [I2] Dropped-image announcement is lost on the `committed_but_unreloaded` arm
- **File:** `packages/client/src/hooks/useSnapshotController.ts:214`
- **Bug:** `droppedImageCount` is assigned at `:177` inside the mutate callback, but the
  announcement sits inside `if (result.ok)` at `:209-216`. Every
  `stage: "committed_but_unreloaded"` return in `useEditorMutation.ts` (`:308`, `:399`,
  `:405`, `:471`, `:477`) is reached **after** `directive = await mutate()` succeeded at
  `:208` — so on that arm the count holds the true value and is simply never surfaced. The
  arm at `:244-268` raises `applyReloadFailedLock` and returns.
- **Impact:** Restore commits with images dropped, the follow-up reload GET fails, and the
  user sees only "Snapshot restored, but reloading the chapter failed. Refresh the page…".
  They refresh and find images missing with no explanation. This contradicts the code's own
  comment at `:210-213` ("announce on BOTH arms" — there are three) and
  `snapshots.service.ts:195-197` ("this is the one place a restore alters what it restores,
  so it must never be silent"). It is the arm where the user is *least* able to see the
  change themselves, since the editor is locked. The 2xx-`BAD_JSON` arm (`:282-347`)
  legitimately cannot announce — the body was unparseable — and is not part of this finding.
- **Suggested fix:** Hoist the `if (droppedImageCount > 0) setActionInfo(...)` block above
  the `result.ok` check. `actionInfo` and the lock banner are separate slots in
  `EditorMainContent.tsx:249-263` and co-display cleanly. Note the new test harness cannot
  express this case: the `mutation.run` stand-in at `useSnapshotController.test.tsx:129-141`
  returns `opts.runResult` at `:131` *before* invoking `cb`, but the real hook reaches this
  stage strictly *after* a successful `mutate()`.
- **Confidence:** Medium
- **Found by:** Logic & Correctness, Error Handling & Edge Cases, Concurrency & State, Contract & Integration, Security, Spec Compliance (`claude-opus-5[1m]`)

### [I3] Upload cleanup skips on error *identity*, not on "did the insert land"
- **File:** `packages/server/src/images/images.service.ts:109` (guard) / `packages/server/src/images/images.repository.ts:8` (unguarded re-read)
- **Bug:** `insert()` does `await db("images").insert(data)` — which auto-commits, since
  `uploadImage` calls `store.insertImage` on the root store outside any transaction — and
  then `await db("images").where("id", data.id).first()`. The new guard matches only
  `AppError` + `READ_AFTER_INSERT_FAILURE`, i.e. the *empty-result* case. If the confirming
  SELECT **throws**, the guard is false and `deleteImageFile(filePath)` runs against an
  already-committed row.
- **Impact:** Identical to the "permanent corruption" the fix's own comment names, in the
  other direction: a committed `images` row pointing at a file that no longer exists, so the
  image 404s forever. Reachable via `SQLITE_BUSY`, I/O error, or most plausibly
  `Knex: Timeout acquiring a connection` — the sqlite pool is `max: 1` with a 60s
  `acquireConnectionTimeout` (`auto-snapshot.ts:30-32`), and `uploadImage` releases the
  connection between the two statements, so a concurrent `store.transaction(...)` can take
  it in the gap. **Nothing repairs the resulting state:** `images.reaper.ts:75-87` deletes
  only files whose uuid has no DB row (`if (known.has(id)) continue`) — it never repairs a
  row without a file.
- **Suggested fix:** Move the discrimination to where the fact lives. After the INSERT, *any*
  failure of the re-read means the row is committed — wrap the re-read in try/catch inside
  the repository and throw `READ_AFTER_INSERT_FAILURE` with `{ cause: err }`.
- **Confidence:** Medium
- **Found by:** Error Handling & Edge Cases (`claude-opus-5[1m]`)
