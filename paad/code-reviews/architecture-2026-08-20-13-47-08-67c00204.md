- **[S1] `initDb` is not failure-atomic, and this branch removed the path that used to heal it** — `packages/server/src/db/connection.ts:52-63`. `db` is published to the module global at `:56`, before the three PRAGMAs and `migrate.latest()` at `:58-61`. No `try`/`catch` destroys the instance or clears the global if one rejects, so the handle is leaked and `getDb()` (which only checks truthiness) hands back a database whose migrations never ran. The old code's `if (db) { await db.destroy(); }` genuinely rebuilt a fresh migrated handle on a retry — verified against `git show main:.../connection.ts` — so the branch's unconditional `throw` removed a real recovery path, and the new message ("Database already initialized — call closeDb() first") is false for exactly this state. #### [OOSS1] Settings key allowlist is bypassable via `Object.prototype` names — backlog id: `4ca1b901`
- **File:** `packages/server/src/settings/settings.service.ts:23` (reached via `settings.routes.ts:21-26`; schema at `packages/shared/src/schemas.ts:132-148`)
- **Bug:** `SETTING_VALIDATORS` is an object literal, so `SETTING_VALIDATORS[key]` walks `Object.prototype`. `key` is constrained only by `z.string().min(1)`. Verified per name: `toString` and `constructor` return a truthy validator, pass the value check, and **commit a junk settings row with 204**; `valueOf` / `hasOwnProperty` / `propertyIsEnumerable` / `__proto__` throw a `TypeError` inside the handler, which `globalErrorHandler` clamps to **500 INTERNAL_ERROR** for a well-formed client body the endpoint's own logic intends to reject with 400. `isPrototypeOf` and ordinary unknown keys are correctly rejected.
- **Impact:** Two failures at one boundary. The allowlist is the only thing between a request body and an arbitrary write into the `settings` key-value table, and there is no DELETE endpoint to remove what gets through — though pollution is bounded (assigning a *string* to `__proto__` in `getAll` is a no-op, so this is contamination, not escalation). The 500 arm violates CLAUDE.md §API Design's rule that client-caused failures are 4xx, the same class of off-taxonomy leak `ERROR_STATUS_ALLOWLIST` was introduced for (I4). Ranked Suggestion because Smudge is single-user with no auth — the "attacker" is the writer — and reaching either arm means deliberately sending a JavaScript builtin name as a settings key.
- **Why out-of-scope:** `settings.service.ts` is not in the touched-lines map. Reasoning-promotion was run and fails: F-25's `.strict()` constrains which *keys are present in the entry object*, not the *value of the `key` field*. The attack body `{"settings":[{"key":"toString","value":"UTC"}]}` has exactly the two declared keys and passes `.strict()` identically before and after this branch.
- **Suggested fix:** Mirror the codebase's own idiom at `apiErrorMapper.ts:120-132` (whose comment already names "C2" and guards attacker-influenced keys for the identical reason): `const validator = Object.hasOwn(SETTING_VALIDATORS, key) ? SETTING_VALIDATORS[key] : undefined;`. A `Map` or `Object.create(null)` works too. Add Supertest cases asserting `{key:"toString"}` and `{key:"hasOwnProperty"}` both answer 400 — `settings.service.test.ts:28` currently exercises only an ordinary unknown key.
- **Confidence:** High (85 — the Verifier raised this above the specialists' 78/79 caps, having confirmed every link by reading and the JS semantics with a throwaway script that touched no repository file)
- **Found by:** Contract & Integration, Security (`claude-opus-5[1m]`)
- **Backlog status:** new

#### [OOSS2] F-29's liveness-check-plus-read atomicity applied at 3 sites; ~11 identical siblings left split — backlog id: `6c588883`
- **File:** `packages/server/src/projects/projects.service.ts:112` (`getProject`), plus `:133` `updateProject`, `:204` `createChapter`, `:248` `reorderChapters`, `:281` `getDashboard`; `packages/server/src/images/images.service.ts:73` `uploadImage`, `:270` `getImageReferences`; `packages/server/src/search/search.service.ts:128` `searchProject`, `:222` `replaceInProject`; `packages/server/src/export/export.service.ts:36`; `packages/server/src/velocity/velocity.service.ts:85`
- **Bug:** Every site has the `findProjectBySlug/ById → if (!x) return null → read/write children` shape across two round trips that F-29's own new comments forbid. The two **write** sites are worse: `uploadImage` lands a file on disk *and* commits an `images` row under a project trashed mid-request; `replaceInProject` rewrites chapter content of a trashed project. The underlying race is verified real, not theoretical: `knexfile.ts` sets no `pool` key, Knex's sqlite3 dialect defaults to `{min:1, max:1}`, Knex issues a real `BEGIN`, and under WAL SQLite pins the read snapshot at the first read — so the transaction genuinely closes the window and the split genuinely leaves it open.
- **Impact:** Reads: wrong status code, no data loss. Writes: a committed row or rewritten chapters under a concurrently-trashed project — a benign ordering ambiguity in a single-user app, recoverable via restore. Triggering any of them needs two concurrent writers against the same entity, which the architecture report's own F-29 deferral note says "a single-user app with a synchronous single-connection SQLite driver does not produce in normal use." The report rates this class Low; this review matches it.
- **Why out-of-scope:** None of these lines is in the touched-lines map — the only touched ranges in these files are `images.service.ts:122-141` (`listImages`, the *fixed* site 50 lines below `uploadImage`), `projects.service.ts:7-13` / `:36-48` (F-30's imports and error class), and `snapshots.service.ts:83-118`. The branch does not change these sites' code, does not make their race likelier, and does not widen its blast radius. The strongest promotion argument offered — that three new comments assert a convention the codebase does not uniformly follow, misleading a future author — is a claim about author guidance, not about the defect firing or growing; the Verifier declined to promote on that basis.
- **Merge note:** three specialists reported overlapping subsets; merged with the union of sites, each verified by reading. One site dropped as a false positive: `getTrash` (`projects.service.ts:314-320`) calls `findProjectBySlugIncludingDeleted`, so reading a soft-deleted project there is the intended behavior.
- **Suggested fix:** Either extend the wrap — prioritising `replaceInProject`, the cheapest of the two writes with no I/O complication — or add one line to F-29's report entry naming which sites were knowingly left split and why. Two caveats: wrapping `uploadImage` would pull filesystem I/O inside a transaction on a `max: 1` pool, which the codebase deliberately avoids elsewhere (see `createChapter`'s comment at `:236-239`), and `getImageReferences` needs `scanImageReferences` (`images.references.ts:291-292`) to accept a store rather than calling `getProjectStore()` itself — precisely the starvation trap the new F-29 comments warn about.
