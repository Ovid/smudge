## Important Issues

### [I1] `applyServerRow` does not run from an async settle — the ref-justification comment misstates why the ref is load-bearing
- **File:** `packages/client/src/components/OuttakesPanel.tsx:159-169` (and the stale return-value note at `:157`)
- **Bug:** The new comment above the `react-hooks/refs` disable says "Both readers below run from an ASYNC settle that can land after a project switch." That is true of `callbacksFor`'s `isCurrent()` (line 244) — `OuttakeCard`'s delete/rename carry no `AbortSignal` and genuinely settle after unmount. It is **false** of `applyServerRow` (line 183): with `handleCreate` deleted, its only remaining call site is the `capturedOuttake` effect at line 207, which runs post-commit with that commit's props, with no `await` between the render-time ref write and the read. The ref is still load-bearing there, but for a reason the comment does not state: `applyServerRow` is `useCallback(…, [reconcile])`, `reconcile` is `useCallback(…, [seq, requestReload])`, `requestReload` is `useCallback(…, [])`, and `seq` is the `useMemo`-pinned object from `useAbortableSequence`. So `applyServerRow`'s identity never changes for the component's lifetime, and a closure over the `projectId` prop would freeze the **first render's** project id permanently.
- **Impact:** The stated justification is checkable and fails the check for one of its two named readers. A future author who verifies "does `applyServerRow` run from an async settle?", finds it does not, and "simplifies" by closing over the `projectId` prop reintroduces exactly the leak the guard exists for. The comment two lines below (`:179-182`) spells out the cost: the leaked row's Insert pastes project A's private text into a project B chapter, and its Delete **hard-deletes** a real project-A outtake (outtakes carry no `deleted_at`). Adding `projectId` to `applyServerRow`'s dep array would be safe — the capture effect's `surfacedCaptureIdRef` guard makes the extra re-run a no-op — but closing over it without that dep would not, and nothing in the comment tells you which.
- **Suggested fix:** Split the rationale by reader — `callbacksFor` needs the live value because its callbacks fire from un-abortable card settles; `applyServerRow` needs it because its `useCallback` deps are lifetime-stable, so any captured `projectId` is the mount-time one. While there: `applyServerRow`'s `: boolean` return is now unread (line 207 discards it; its only prior consumer was `handleCreate`'s `S.createdElsewhere` branch), so either drop the return or re-consume it, and update the "Returns whether the row was accepted (S2)" note at line 157.
- **Confidence:** Medium (74)
- **Found by:** Concurrency & State (`claude-opus-5[1m]`)
