## Executive Summary

One Critical finding, reproduced end-to-end by two independent agents: the branch's
own OOSI1 fix — the `throw` added to `runRestore` so a tampered backup archive can
no longer restore to an empty data directory while reporting success — is bypassed
by a single character. Its directory carve-out asks whether the *central-directory

## Critical Issues

### [C1] The OOSI1 directory carve-out is a one-character bypass — the silent-data-loss bug survives the fix meant to close it
- **File:** `packages/server/src/backup/backup-core.ts:299`
- **Bug:** The new guard decides "is this entry a directory?" from the
  **central-directory name string** (`name.endsWith("/")`), but the disagreement it
  guards against is between the central-directory name space and JSZip's map, which
  is keyed by each entry's **local header** name. JSZip's `readLocalPart` sets
  `fileNameStr`, and that string both keys the map (`jszip/lib/load.js:65-66`) and
  drives the trailing-slash directory fail-safe (`jszip/lib/zipEntry.js:154-157`);
  the central name never enters JSZip's map at all. So whoever produced the archive
  controls the carve-out independently of the entry's real content.

  Reproduced twice independently. Patching one archive's central-directory name from
  `images/proj-1/a.png` to `images/proj-1/a.pn/` — same byte length, so no offsets
  shift and every pre-move check still passes — while leaving the local header
  untouched gives:

  ```
  JSZip map keys: [ 'smudge.db', 'images/', 'images/proj-1/', 'images/proj-1/a.png' ]
  zip.file("images/proj-1/a.pn/") -> null
  central names:  [ 'smudge.db', 'images/', 'images/proj-1/', 'images/proj-1/a.pn/' ]
  runRestore RESOLVED: { movedAsideTo: '.../data.before-restore-...' }
  restored dataDir: [ 'smudge.db' ]
  ```

  Line 299 sees the trailing slash, treats the entry as one of `runBackup`'s
  auto-created folders, and `continue`s. The image is silently dropped and
  `runRestore` **resolves successfully**.

  A second, latent inconsistency sits alongside it: the destination path at line 326
  is built from the **central** name while `bytes` come from an entry JSZip keyed by
  the **local** name, so a file can in principle be written under a name it does not
  carry locally.

  Note on the apparent contradiction in the specialist evidence: the Error Handling
  specialist verified that JSZip forces `dir = true` for any name ending in `/`, so
  the two classifications "agree by construction". That is correct — but only when
  the central name and the local name are the *same string*, which is always true for
  Smudge-produced archives and never true for the tampered archive this finding
  describes. Both claims are right within their stated scope; they never overlapped.
- **Impact:** Total silent data loss during disaster recovery, with a success report
  to the operator — verbatim the OOSI1 outcome this change was written to eliminate.
  The precondition (a tampered or corrupt archive) is the change's own stated threat
  model, not an exotic assumption. The operator restores, is told it worked, and
  discovers the missing images later with the move-aside directory possibly already
  cleaned up.
- **Suggested fix:** Ask JSZip what the entry *is* rather than inferring it from an
  untrusted string. `zip.files` is public and typed (`jszip/index.d.ts:210`), and
  JSZip normalizes every folder key to a trailing slash (`folderAdd` →
  `forceTrailingSlash`):

  ```ts
  const entry = zip.files[name] ?? zip.files[`${name}/`];
  if (!entry) {
    throw new Error(
      `archive entry declared in the central directory but not extractable: ${JSON.stringify(name)}`,
    );
  }
  if (entry.dir) continue;
  const bytes = await entry.async("nodebuffer");
  ```

  This also closes [S1] (the attribute-bit directory regression) and, with the
  `JSON.stringify`, [S3] (the unescaped echo) in the same edit. Add a test using the
  equal-byte-length central-name patch above — the existing OOSI1 test patches the
  *local* name, which is the direction that already works.
- **Confidence:** High (95)
- **Found by:** Logic & Correctness — server (`claude-opus-5[1m]`), reproduced by Verifier (`claude-opus-5[1m]`)

## Suggestions

- **[S1]** `packages/server/src/backup/backup-core.ts:299-302` — A directory entry marked by the MS-DOS attribute bit (external file attributes `0x10`) instead of a trailing slash now hard-aborts a restore that previously succeeded. `jszip/lib/zipEntry.js:143` sets `dir` from the attribute bit and only *then* falls back to the trailing slash (line 156, commented "fail safe"), and `walkCentralDirectory` never reads that field. Reproduced: `zip.file("images/p")` returns null, `"images/p".endsWith("/")` is false, the throw fires, and the operator is left with a half-populated data dir plus a move-aside to recover by hand — for an archive JSZip itself parses without complaint. Genuine regression (pre-change, `if (!file) continue` correctly skipped it), but no mainstream producer writes attribute-only directory entries and `docs/backup.md` scopes restore to Smudge's own archives. Closed by C1's fix. *(Medium, 62 — Logic & Correctness server + Contract & Integration)*
- **[S2]** `packages/client/src/hooks/useSnapshotController.ts:287` — `reassertEditorEditable()` cannot reach TipTap in the drift case it was added for, though that case is currently unreachable in production.
