### [S1] `maxLength` comment asserts the inverse of the actual client/server cap relationship

- **File:** `packages/client/src/components/SnapshotPanel.tsx:420-424` (the same claim is restated at `packages/client/src/__tests__/SnapshotPanel.test.tsx:317-320`)
- **Bug:** The comment reads *"Never stricter than the server, which trims and sanitizes before measuring, so this cannot reject a label the API would have accepted."* The stated premise yields the opposite conclusion. `sanitizedLabelBase` (`packages/shared/src/schemas.ts:211-214`) is `.max(5000)` → `.transform(sanitizeSnapshotLabel)` → `.pipe(z.string().trim().max(LABEL_MAX_UNITS))`. `sanitizeSnapshotLabel` (`schemas.ts:139-150`) *deletes* characters — C0/C1 controls, bidi overrides, line/paragraph separators, zero-width characters — and `.trim()` then removes surrounding whitespace. So the server measures a string that is only ever shorter than or equal to the raw input, while HTML `maxLength` measures the raw value. The server accepts a strict **superset**; the client cap is the stricter side.
- **Impact:** Two costs, and the smaller one is the data cost. A label whose raw length exceeds 500 UTF-16 code units but whose sanitized-and-trimmed length does not — realistically a title pasted from a word processor or web page carrying zero-width joiners, a BOM, or bidi marks — is silently truncated by the browser at 500 raw units before `handleCreate` sends it (`SnapshotPanel.tsx:316`). No message is shown. That is small: labels are short, and nothing in the manuscript is affected. The larger cost is to reasoning. This comment is the stated basis for the report's F-34 claim that the new server code and scope copy are "unreachable from the shipped UI, deliberately" (report line 634). That reachability claim rests on the inverted inference, so a future reader who trusts the comment could delete the `SNAPSHOT_LABEL_TOO_LONG` arm as dead code, or carry the same inference to a field whose sanitizer strips more.
- **Corroborating evidence in the schema itself:** `sanitizedLabelBase`'s own comment says the 5000 pre-cap exists to leave "room for sanitizer-stripped bidi/control chars without gatekeeping legitimate long labels that would fit once cleaned" — the schema is explicitly designed for the case the client comment says cannot occur.
- **Suggested fix:** Keep `maxLength` — it is the right guard, at the boundary where the writer can see it. Correct the claim to state the real property: the cap matches the schema's post-sanitize unit but is applied pre-sanitize, so it can truncate a raw label that would have survived cleaning. Fix the duplicated claim in `SnapshotPanel.test.tsx:317-320` in the same edit. The untouched precedent at `OuttakeCard.tsx:259-261` carries a narrower version of the same error and is logged separately below as `[OOSS1]`.
- **Confidence:** Medium (merged 74)
- **Found by:** Logic & Correctness and Error Handling & Edge Cases (`claude-opus-5[1m]`) — raised independently by both lenses
- **Status:** Fixed 2026-08-19, same sitting as this review. Both the attribute comment and its restatement in the test now state the real property. The test comment no longer restates the reasoning at all — it says it pins the number only and points at the attribute, so there is one owner of the explanation rather than two copies free to drift.
- **Status correction (this finding overreached on one point):** the entry above says the bad comment is "the stated basis" for the report's F-34 claim that the server cap path is unreachable from the shipped UI. That is wrong, and re-checking it is what surfaced the error. The F-34 note (`…-architecture-report.md:634`) grounds unreachability solely on `maxLength` capping the raw input at 500 — and that holds independently: sanitizing and trimming only delete characters, so a raw value of at most 500 units cannot exceed 500 after either. ### [S4] New tests land in a suite with no RTL cleanup, so the F-32 safety net skips the teardown path it exists to pin

- **File:** `packages/client/src/hooks/__tests__/useKeyboardShortcuts.test.tsx:233-297` (the new F-32 describe); second site at `packages/client/src/__tests__/EditorPageImageAnnouncement.test.tsx:132-134`
- **Bug:** React Testing Library registers its own `afterEach` cleanup **only** when `afterEach` is a *global* (`node_modules/@testing-library/react/dist/index.js:23-26`, guarded by `typeof afterEach === 'function'`). `packages/client/vitest.config.ts` sets `environment`, `setupFiles`, and `slowTestThreshold` but has no `globals` key, so Vitest never defines `globalThis.afterEach`; the setup file imports `afterEach` from `vitest` as a module binding, which does not satisfy RTL's check. Auto-cleanup is therefore off. `useKeyboardShortcuts.test.tsx` calls `renderHook` at lines 54, 131, 182, and 240 and contains no `cleanup()`, no `unmount()`, and no `afterEach` — `cleanup` is not even imported. So no rendered hook is ever unmounted, each test leaves a live `document` keydown listener behind, and the hook's effect cleanup (`useKeyboardShortcuts.ts:251-255`) never runs in this file. That cleanup is the only code that sets `unmounted = true` and clears the pending `navAnnouncementTimer`.
- **Impact:** The new F-32 tests exist specifically to pin that timer's behaviour, and they cover none of its teardown — the one lifecycle hazard a dwell timer actually has (firing after teardown) is the one thing this safety net cannot detect. **No assertion is wrong today**, and the reason was confirmed: every `renderHook` call passes a fresh private `vi.fn()` for `setNavAnnouncement` (`setupAndSettle` allocates its own at line 234), so the stale instances that also handle the new describe's `fireEvent.keyDown(document, …)` write to mocks nobody asserts against. This is a leak plus a named hole in a safety net, not a live race. The latent cost is that any future assertion in this file against a shared observable (`document`, a module-level spy, `screen`) will see N hook instances instead of one, and the failure will present as a race rather than as a leak. The second site is the same hole in a second place: `EditorPageImageAnnouncement.test.tsx:132-134` runs `vi.useRealTimers()` *before* `cleanup()`, so by the time `EditorPage`'s unmount effect (`EditorPage.tsx:576-582`) calls `clearTimeout`, the fake clock is gone and the handle is meaningless. Nothing leaks there — `vi.useRealTimers()` already discards pending fake timers — but that file likewise cannot regress-detect a removed unmount cleanup.
- **Suggested fix:** Add `afterEach(cleanup)` to `useKeyboardShortcuts.test.tsx`, and capture `const { unmount } = renderHook(...)` in `setupAndSettle` so one test asserts the pending timer is cleared on unmount (settle, `unmount()`, advance by `DWELL_MS`, assert `setNavAnnouncement` was never called with the empty string). In `EditorPageImageAnnouncement.test.tsx`, swap the `afterEach` body to `cleanup(); vi.useRealTimers();`.
