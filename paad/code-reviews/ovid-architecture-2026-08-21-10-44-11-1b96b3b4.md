### [I1] `writeChapterContent`'s comment promotes a caller obligation into a helper guarantee

- **File:** `packages/server/src/snapshots/snapshots.service.ts:281-283` (and the `@param` block at `packages/server/src/chapters/chapter-content-write.ts:44-47`)
- **Bug:** The helper stores `args.nextContent` (`chapter-content-write.ts:51-52`) and counts `countWords(args.nextDoc)` (`:53`) — two independent caller-supplied parameters with no assertion, no derivation of one from the other, and no type-level link. The new comment at the restore call site says "`writeChapterContent` is what enforces that agreement: it derives the word count from the same document it stores." It does not; it co-locates two reads of a pair the caller must keep in sync.
- **Impact:** `restoreSnapshot` keeps the pair in sync with a hand-written second assignment — `restoreContent = JSON.stringify(stripped);` immediately followed by `newParsed = stripped;` (`snapshots.service.ts:235-236`). A future edit that adds another conditional transform of `restoreContent` above the call and drops that second line stores the stripped document while `word_count` describes the pre-strip one. That miscount is read by the dashboard aggregate and by `updateDailySnapshot`'s `sumChapterWordCountByProject`, so the writer's reported daily progress is wrong with no error anywhere — precisely the failure the helper's own doc comment (`:8-11`) says it exists to prevent. Latent today: the one divergent path (`docObj.content = []` mutated in place at `:180` when the snapshot is a schema-valid `{"type":"doc"}`) counts 0 words either way.
- **Suggested fix:** Reword, do not enforce. The two-parameter shape is correct and deliberate: `replaceInProject` needs the serialized bytes before the call for its `MAX_CHAPTER_CONTENT_BYTES` check, and `restoreSnapshot` must write the snapshot's exact stored bytes rather than a re-serialization. State the contract as a caller obligation at both `snapshots.service.ts:281` and the `@param` block, as the pre-refactor comment correctly did ("must all agree on ONE content value").
- **Confidence:** Medium

### [I2] Rule 2 violated twice: the fix commit carries its own `Status:` block, and the SHA-correcting tip is tagged `[chore]`

The decision doc's own diagnostic paragraph (`:89-95`) predicts this failure by name and records it as the third recurrence.
- **Suggested fix:** `1b96b3b4` is the branch tip with nothing after it, so the rebase-invalidates-recorded-SHAs objection that spared the earlier recurrences does not apply here — one `git commit --amend` retags it to `docs(report): [F-03] correct F-03's Status commit SHA`.
