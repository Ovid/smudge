## Important Issues

### [I1] `writeChapterContent`'s rationale names a garbage-collection path that does not exist
- **File:** `packages/server/src/chapters/chapter-content-write.ts:21-26`
- **Bug:** The doc comment justifies the content/ref-count coupling with "Writing content without re-running `applyImageRefDiff` leaves an image referenced by the chapter but counted as unreferenced, so the reaper garbage-collects a picture that is still on the page." The reaper does no such thing. `reapOrphanImages` (`packages/server/src/images/images.reaper.ts:41-90`) selects `id` from `images` and deletes files whose id has **no DB row** — it never reads `reference_count`. Grep for `reference_count` outside tests returns three production sites (`images.repository.ts:90,99`, `images.service.ts:234`); none is a GC path.
- **Impact:** This is the sentence a future session reads when deciding what the ref-count obligation is worth, and it asserts silent data loss where the truth is cosmetic. The real consumer of a drifted count is `ImageGallery.tsx:456,466,486` — the "unused" badge and the delete-confirmation `isUsed` gate — so a used image gets labelled unused. The delete is still blocked, because `images.service.deleteImage:207-231` gates on a live `scanChapterContentForImage` rather than on the counter, and that same path self-heals the drift via `setImageReferenceCount(id, activeRefCount)` at `:234`. Overstating the stakes is the mirror of understating them: it teaches the next reader a false model of image GC, which they will then apply to a real GC decision.
- **Suggested fix:** Replace the reaper clause with the true consumer — e.g. "…leaves `reference_count` describing the previous revision, so the gallery labels a used image 'unused' until `deleteImage`'s live scan corrects it." Keep the second half of the sentence (`word_count` → dashboard/velocity), which is accurate. Note the same wrong belief pre-exists at `images.references.ts:82-83` on `main` and is presumably where this copy came from; that instance is outside this branch's blame and is not filed here, but fixing only the new copy leaves the source.
- **Confidence:** High
- **Found by:** Contract & Integration (`claude-opus-5[1m]`)
