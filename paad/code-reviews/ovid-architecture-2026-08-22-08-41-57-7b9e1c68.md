### Out-of-Scope Important

#### [OOSI1] Nothing at any level tests that a locked editor can become writable again — backlog id: `8ff156ec`
> **Added 2026-08-22 by a `/paad:rethink` verification pass, not by the original review.** It
> surfaced when the repository owner challenged the premise under [I1] — that recommending a
> lock is only sound if there are trustworthy, tested ways back out of one. Checking that
> premise is what found this. It is the reason [I1]'s code half was withdrawn: the risk this
> finding names is materially larger than the one that change would have addressed.

- **File:** `e2e/editor-save.spec.ts:107` (where the only end-to-end lock test stops), and the
  editor-lock test surface generally
- **Bug:** The editor's persistent read-only lock has **zero tests, at any level, that
  demonstrate a writer getting back to work after one.** The inventory: five reducer unit tests
  assert the lock field becomes `null` (`useEditorMutationMachine.test.tsx:47,54,70,80,91`); two
  hook tests replay a dispatched-event list through the reducer by hand and assert the folded
  result (`useEditorMutation.test.tsx:1687,1706`); nineteen component tests in
  `EditorPageFeatures.test.tsx` name the lock, of which six assert it *appears*, ten assert
  something is *refused* while it stands, and the rest assert it was never raised; and the one
  end-to-end test (`e2e/editor-save.spec.ts:49-107`) intercepts a save with a 404, waits for the
  banner, asserts `contenteditable === "false"`, and ends. Nothing renders a locked editor and
  then shows it accepting input again.
  The counterfactual was checked by exhaustive grep rather than assumed: break the unlock
  transition tomorrow — make `EDITOR_REMOUNTED` preserve the lock instead of clearing it — and
  exactly **two** reducer unit assertions go red (`useEditorMutationMachine.test.tsx:70-78`,
  `:80-89`). Zero component tests and zero end-to-end tests. That event also fires on every
  ordinary mount from the initial state, where the lock is already `null`, so preserving it
  changes nothing observable in any rendering test.

  **Correction (2026-08-22, from running the experiment rather than reasoning about it).** The
  grep prediction was exactly right — the mutation was applied and the suite reported `2 failed |
  1899 passed`, both failures in `useEditorMutationMachine.test.tsx`. But the **interpretation
  was wrong**, and the error mattered. That break is not a coverage gap: `EDITOR_REMOUNTED`'s
  `lock: null` is **unreachable in production**. The event fires from an effect keyed on
  `[activeChapter?.id, chapterReloadKey]`, and while a lock stands neither dependency can move —
  `chapterReloadKey` only advances inside `reloadActiveChapter`, which only `run()` calls, and
  every `run()` caller refuses while locked; every path that changes the active chapter is
  likewise refused. So no end-to-end test *could* catch that break, and the two reducer
  assertions failing is the correct amount of coverage for a defensive arm whose lock-clearing
  half never executes. The reducer's own comment ("Chapter switch or post-reload remount: the
  prior lock no longer applies") describes a situation that cannot arise while a lock is up.
  **The finding survives; its evidence changes.** The real exits are the two named below — a full
  page reload and a route unmount — and *neither passes through the reducer at all*, which is
  precisely why a reducer-level counterfactual said nothing useful about them. Both are now
  covered by end-to-end tests whose load-bearingness was verified by breaking each exit
  independently and watching the matching test fail (see Status below).
- **Impact:** The lock is genuinely reachable in ordinary use, and not by the exotic route [I1]
  described. An autosave PATCH returning 404 — the chapter deleted or purged out from under an
  open editor — raises the identical non-dismissible lock via `chapter.save`'s `terminalStatuses`
  (`scopes.ts:237`, `useProjectEditor.ts:666-671`). That is the case the existing end-to-end test
  already exercises. Once raised, the lock is an in-editor dead end, and that is not a guess: the
  three events that clear it all dispatch from inside `useEditorMutation.run()`, and all three
  `run()` callers refuse at entry while locked (`useFindReplaceController.ts:225,505`,
  `useSnapshotController.ts:134`); the remount event's two dependencies are both frozen for the
  same reason (`chapterReloadKey` only moves inside `reloadActiveChapter`, which only `run()`
  calls; `activeChapter.id` only moves through paths that refuse while locked); and `UNLOCK` has
  no production dispatcher at all — verified by grep, not by trusting the reducer's comment.
  So the recovery surface is exactly two things: the banner's Refresh button, which does a real
  `window.location.reload()` (`EditorMainContent.tsx:231-241`), and the undocumented logo route
  described in [S7]. **Both are untested as exits.** A regression in either ships silently and
  strands a writer in a read-only editor — the outcome the lock exists to make safe becomes the
  outcome that makes the app unusable.
  One structural fragility worth recording alongside it: the banner renders *above* the
  view-mode branch, so it survives trash view, dashboard, preview, and the empty-project state.
  That universality is incidental, not enforced. A future early return added above
  `EditorMainContent` would hide the only documented escape hatch, and no test would notice.
- **Suggested fix:** An end-to-end test that raises the lock the reachable way (the existing 404
  interception), clicks Refresh, and asserts the writer can type again. One design note found
  while verifying: that test's route interception blocks only PATCH, so after the reload the
  chapter loads normally and the editor returns writable — but typing again re-triggers the 404
  and re-locks after the debounce. Assert "the editor is writable and the banner is gone" rather
  than "typing then saves successfully," or drop the interception before reloading. Add a second
  test for the logo-and-back route, since it is currently load-bearing by accident. Consider a
  guard test pinning that the lock banner renders above every view branch.
- **Status: FIXED 2026-08-22** (`e2e/editor-save.spec.ts`). Two tests added, each pinning one
  exit, both raising the lock the reachable way via the existing PATCH-404 interception:

  asserts not just a writable box but that typing reaches the server again — the save status
