### [I1] `multerLimitError`'s `LIMIT_` prefix guard leaves malformed multipart landing as 500 INTERNAL_ERROR
- **File:** `packages/server/src/images/images.routes.ts:48-61` (guard at `:50`), consumed at `:90`
- **Bug:** The guard `if (!code?.startsWith("LIMIT_")) return null;` classifies only the seven `LIMIT_*` codes. Two client-error shapes escape it, both verified by execution:
  - **multer's own `MISSING_FIELD_NAME`** — the one code in `node_modules/multer/lib/multer-error.js` that does not begin `LIMIT_`. Raised at `make-middleware.js:164` when a file part carries `filename` but no `name`. Busboy 1.6.0 emits `file` with `fieldname === undefined` for `Content-Disposition: form-data; filename="a.png"`, and multer's `if (fieldname == null) return abortWithCode('MISSING_FIELD_NAME')` fires.
  - **busboy's constructor rejections, which carry no `code` at all** — `"multipart/form-data"` (no boundary) throws `Error "Multipart: Boundary not found"` with `code=undefined`; `"multipart/form-data; boundary="` throws `"Malformed content type"`; `"multipart/mixed; boundary=xyz"` throws `"Unsupported content type…"`. multer catches these at `make-middleware.js:126-131` and hands the bare `Error` to this callback.

  Both take the `return null` path, `:90`'s `?? err` forwards the raw error, and `globalErrorHandler` (`app.ts:168-173`) computes `rawStatus = 500` -> `INTERNAL_ERROR` plus an error-level `"Unhandled request error"` log.
- **Impact:** The function's doc comment asserts "Only LIMIT_FILE_SIZE was mapped, so **the rest** reached globalErrorHandler carrying no status and were clamped to 500 — a client mistake recorded as a server fault." That class is not closed. This is not a regression (both shapes reached 500 before the branch too), but it is the branch's own stated deliverable, delivered incompletely under a comment that reads as if it were complete. It also writes error-level lines into the anomaly-log channel CLAUDE.md §F-2 rests on.
- **One defect, two triggers:** the verifier merged these deliberately. They share a single root cause — the guard is keyed on a prefix rather than on "is this the client's fault?" — and a single fix closes both. Both sub-cases are named so a partial fix stays visible.
- **Suggested fix:** Key on the question rather than the prefix — after the two specific arms, `return new BadRequestError("Malformed file upload.")` for any non-`AppError` reaching this callback. Minimally, add `MISSING_FIELD_NAME` to the enumerated codes and a message-shape arm for the busboy constructor errors. Add a test posting `Content-Type: multipart/form-data` with no `boundary=`.

### [I3] `docs/deferred-issues.md` marks the CORS half of a deferred security issue "Resolved" on a justification that does not apply to it
- **File:** `docs/deferred-issues.md:66` and `:72` (the new "Resolved 2026-08-22" block); code discussed at `packages/server/src/app.ts:60-65`
- **Bug:** The block at `:66` says "All three parts are now closed", and `:72` justifies omitting the Origin/CORS allowlist because it would "defend against an attack `Host` validation already blocks." Those are two different attacks:
  - **DNS rebinding** — the attacker's own hostname lands in `Host`, which is why `isLoopbackHost` catches it. The substitution argument is correct here.
  - **Ordinary cross-origin request from a page the writer is browsing** — the browser puts the *genuine* `localhost:3456` in `Host`, so `isLoopbackHost` returns `true` **by design** and the request is served. Nothing else stops it: grepping `cors|Access-Control|Origin|Sec-Fetch` across `packages/server/src` (excluding tests) returns only the three F-02 comment lines. No `cors` dependency, no auth.
- **Verified CSRF surface:** `POST /api/projects/:slug/chapters` (`projects.routes.ts:58`) calls `ProjectService.createChapter(req.params.slug)` and reads **no body at all**. A bare auto-submitting `<form method="POST">` is `application/x-www-form-urlencoded`, a CORS-safelisted content type, so no preflight is issued and the chapter is created using only a guessable slug. `POST /api/chapters/:id/restore` likewise reads only `:id`. `POST /api/projects/:projectId/images` is `multipart/form-data`, also safelisted and also sent without preflight — its only protection is that `requireUuidParam` demands a project UUID an attacker cannot read cross-origin.
- **Impact:** The honest severity bound is a write-side nuisance — reads execute but are unreadable cross-origin, and JSON/DELETE mutations do trigger a preflight that no CORS header answers, so they stay blocked. The real cost is bookkeeping: `docs/deferred-issues.md` is where a future session goes to find open work, and this entry now says the gap is closed.
- **Suggested fix:** Reword `:66-72` to close only the helmet / rebinding / network-exposure parts and leave the cross-origin item open, naming which half stands on browser preflight defaults. If a control is wanted, the cheap one is requiring a custom header (`apiFetch` already controls its own headers) on state-changing methods — a custom header forces a preflight even for multipart. That is a decision to record, not a change to slip into this branch.

### [I6] `isLoopbackHost`'s bracketed-IPv6 branch truncates instead of validating — `[::1]evil.com` is accepted
- **File:** `packages/server/src/config/loopback.ts:41-45`
- **Bug:** The `[` branch takes `host.slice(0, host.indexOf("]") + 1)` and discards everything after `]` without asserting that what follows is end-of-string or `:port`. The unbracketed sibling is stricter by construction. Separately the IPv4 arm `/^127(?:\.\d{1,3}){3}$/` range-checks nothing. Verified by execution against the exact source:

  ```
  "[::1]evil.com"    => true      "[::1].evil.com"  => true
  "[::1]x"           => true      "[::1]:"          => true
  "127.999.999.999"  => true      "localhost."      => false
  ```
- **Impact:** Neither bypass spelling is reachable today — the WHATWG URL parser rejects both so no browser can produce them, and the 127.0.0.1 bind stops off-host clients opening a socket. It is **latent, not live.** But this function's own doc block and the `docs/roadmap.md` 7g.1 amendment both state the plan is to widen the bind and widen `isLoopbackHost` "in step." The moment the bind widens — Docker, a LAN mode, or an nginx `proxy_pass http://127.0.0.1:3456` with the default `Host: $proxy_host` re-exposing the port — this function is the *only* control, and a hand-crafted `Host: [::1]evil.com` from a non-browser client walks past it. Rated Important rather than Suggestion because 7g.1 is a planned phase, not a hypothetical, and the fix is two lines.
- **Secondary, lower priority:** `localhost.` (FQDN trailing dot, which a browser sends verbatim for `http://localhost./`) currently 400s — a fail-closed false negative, a usability edge rather than a hole.
- **Suggested fix:** Anchor both arms — `const m = /^(\[[^\]]*\]|[^:]*)(?::\d*)?$/.exec(host); if (!m) return false;` — and range-check the IPv4 octets, or hand the bare host to `node:net`'s `isIP` after stripping the port.
- **Confidence:** High (80) — CONFIRMED
- **Found by:** Security, Logic & Correctness (`claude-opus-5[1m]`)

### [I7] The branch's only security control fires completely silently, under a comment asserting the opposite
- **File:** `packages/server/src/app.ts:52` (the claim) and `:60-65` (the middleware); mechanism at `:130-151` and `logger.ts:16-17`
- **Bug:** Traced link by link, all four confirmed against the tree:
  1. `requestContext` (`requestContext.ts:38-55`) does run first and assigns `req.id`/`req.log` plus the `X-Request-Id` header — but its only per-request log is `req.log.debug` on `finish` (`:52-53`).
  2. The middleware throws `BadRequestError(…, "INVALID_HOST")` — a **400** `AppError`.
  3. `globalErrorHandler`'s `AppError` branch logs **only when `err.status >= 500`** (`app.ts:139`) and returns. 4xx `AppError`s are deliberately silent.
  4. `logger` defaults to level `info` (`logger.ts:7,17`), so the debug access log is suppressed.

  So `app.ts:52`'s "Runs after `requestContext` so a rejection is traceable" is false at default configuration: an `INVALID_HOST` rejection writes **nothing** to the server log, and the response carries an `X-Request-Id` matching no log line.
- **Impact:** Four separate costs:
  - **Observability (OWASP A09).** A DNS-rebinding attempt is indistinguishable in the logs from nothing having happened, and the rejected `Host` value — the single most diagnostic field — is never recorded.
  - **Internal inconsistency with this same branch.** F-34's entire content is converting a silent skip into an observable warning, on the argument that a guard nobody can see is a guard nobody can verify. The Host check deserves at least the treatment the image ref-count skip just got.
  - **Fingerprinting.** Because rebinding makes the attacker's page same-origin from the browser's view, the attacker *can* read the 400 body, so `{"code":"INVALID_HOST"}` plus the `X-Request-Id` header is a positive Smudge fingerprint on `127.0.0.1:3456`. The body correctly does not echo the `Host` (no reflection) — but with no server-side log, the sweep leaves no record on the victim's side either.
  - **Misconfiguration is undiagnosable.** `grep -rn "INVALID_HOST" packages/client/src` returns **zero hits**. A user whose deployment sends a non-loopback `Host` sees per-scope generic copy ("Failed to load project", "Save failed. Try again.") on every endpoint at once. `chapter.save`'s `terminalStatuses` is `[404]` (`scopes.ts:237`), so 400 is not terminal and auto-save burns its full retry ladder on a condition that can never succeed.
- **Not a "consider logging" suggestion:** the defect is a code comment asserting a property the surrounding contract explicitly denies. Either the comment or the behaviour is wrong.
- **Suggested fix:** `req.log.warn({ host: String(req.headers.host).slice(0, 128) }, "Rejected non-loopback Host")` immediately before the throw — truncate, it is attacker-controlled. Or drop the "so a rejection is traceable" clause and say what the ordering actually buys.
- **Confidence:** Medium (70) — CONFIRMED
- **Found by:** Error Handling & Edge Cases, Contract & Integration, Security (`claude-opus-5[1m]`)
