### [I1] `findEocdOffset` now rejects any zip with trailing bytes after the EOCD comment
- **File:** `packages/server/src/backup/backup-zip-format.ts:47` (consumer: `packages/server/src/backup/backup-core.ts`, `runRestore` step 1 via `readCentralDirectorySizes`)
- **Bug:** The new accept condition is an exact equality, `i + 22 + buf.readUInt16LE(i + 20) === buf.length`. Any bytes after the declared comment — block/NUL padding from a transfer or archiving tool, a zip embedded at the head of a larger file — make every candidate fail, so `findEocdOffset` returns `-1` and `walkCentralDirectory` throws `DecompressionBombError("not a valid zip (no EOCD)")`.
- **Impact:** Three compounding problems. (a) This is the data-recovery path — `make restore` is what an operator reaches for after losing data, and the entry being closed asked for **more** archives to be accepted, not fewer. (b) The message asserts there is no EOCD when there is one that simply failed a new equality. (c) `DecompressionBombError` is the class this codebase reserves for **attack** refusals, deliberately separated from `RestorePreconditionError` so an operator can tell "your archive is malicious" from "your archive is not restorable right now". Smudge's own JSZip-written backups carry no comment and no padding, so the exposure is foreign or round-tripped archives.
- **Verified by execution:** a clean JSZip archive gives offset 105 under both the old and the new scan; the same buffer with 16 trailing NUL bytes gives old 105, **new -1** — and `JSZip.loadAsync` on the padded buffer still loads it, keys `['smudge.db']`.
- **Suggested fix:** Keep the length-exact match as the *preferred* candidate and fall back to the last bare signature when none satisfies it (two lines) — or keep the strictness and give it its own honest error class and message. See I3 for the fix that resolves I1, I2 and I3 together.
- **Confidence:** High
- **Found by:** Logic & Correctness, Error Handling & Edge Cases, Contract & Integration, Security (`claude-opus-5[1m]`) — four independent lenses

### [I3] The new selection rule splits Smudge's validating parser from JSZip's extracting parser, and the doc comment claims more than the check delivers
- **File:** `packages/server/src/backup/backup-zip-format.ts:35-47` (`findEocdOffset` doc comment and body)
- **Bug:** Before this change both parsers selected the EOCD by the identical rule — "last signature in the file" — so they agreed on which central directory was authoritative *by construction*. The new line makes Smudge's select "last signature whose declared comment length reaches exactly EOF". The two rules can now pick different records. Separately, the doc comment's claim that "a decoy sitting inside that comment reads an arbitrary length there and (all but certainly) misses" is a probabilistic argument that only holds for **accidental** collisions — an attacker controls every comment byte.
- **Impact:** Zip-slip stays closed: the write destination is built from the validated name, and every validated name must be present in JSZip's key space or restore aborts. What a differential **can** substitute is the content and declared size of a same-named entry — `checkDeclaredSizes` runs on Smudge's central directory while `file.async("nodebuffer")` inflates whatever jszip's directory points at, fully into RAM before the cumulative-byte check. That residual is already filed as backlog `fa8e879a`, which is what caps this at Important rather than Critical. The codebase already treats parser agreement as load-bearing: the F-14 forged-archive test fixes up the EOCD counts, size and offset "so **both parsers agree** the forged record is part of the directory".
- **Verified by execution:** two parsers, two answers, same bytes (396 vs 418). And writing a fake signature into a 60-byte comment with its two length bytes set so `decoy + 22 + len === buf.length` makes the new scan return the decoy at 117 while the true record sits at 91 — two bytes of attacker choice.
- **Suggested fix (smallest, and it also fixes I1 and I2):** keep "last signature wins" as the **selection** and treat the comment-length equation as an accept/reject test on that single candidate. Both parsers then pick the same offset, and a malformed archive is refused with a message that says what is true. Amend the comment either way.
- **Confidence:** High
- **Found by:** Logic & Correctness, Security (`claude-opus-5[1m]`)

### [I8] The new `invalidHost` copy tells the operator to do the one thing the Host allowlist is guaranteed to reject
- **File:** `packages/client/src/strings.ts` (`STRINGS.error.invalidHost`)
- **Bug:** The new string ends "... if it runs behind a proxy, that proxy must forward the original address." `isLoopbackHost` (`packages/server/src/config/loopback.ts`) returns true only for `localhost`, `localhost.`, `[::1]`, and `isIP(bare) === 4 && bare.startsWith("127.")`. A proxy that *forwards the original address* — preserves the browser's `Host`, say `smudge.example.com` — produces exactly the header that fails that test, so following the advice guarantees a permanent 400 `INVALID_HOST` on every request.
- **Impact:** This is remediation guidance attached to a DNS-rebinding defence. An operator who follows it sees the app still fully broken on every endpoint at once, and the two obvious next moves both dismantle the control: widen `isLoopbackHost` to admit their public hostname, or teach the middleware to trust `X-Forwarded-Host` (it currently reads raw `req.headers.host`, which is correctly un-spoofable). Either move re-opens architecture finding F-02. The working configuration is the opposite one and the repo documents it twice: `app.ts`'s own comment says `make dev` and `make e2e` are unaffected "because Vite proxies `/api` with `changeOrigin: true`, so the server sees the proxy target's host" — and `changeOrigin: true` **rewrites** `Host` to the target's host. That is the only proxy configuration in the tree, and it is a Host-rewriting one.
- **Suggested fix:** Drop the proxy clause — the first sentence is complete, correct advice for every deployment that exists today. Or state the actual requirement: the proxy must **present a loopback `Host`** to Smudge (`proxy_set_header Host 127.0.0.1:3456;`). Do not phrase it as preserving the original.
- **Confidence:** Medium
- **Found by:** Security (`claude-opus-5[1m]`)
