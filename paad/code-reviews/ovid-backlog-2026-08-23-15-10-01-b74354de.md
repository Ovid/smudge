### [I1] The new non-idempotent-scope sweep executes zero assertions for 4 of its 5 scopes, and the comment it rests on states the inverse of the behaviour
- **File:** `packages/client/src/errors/apiErrorMapper.test.ts` — `describe("I4 — non-idempotent scopes never invite a 5xx retry")`; comment at `packages/client/src/errors/scopes.ts`, `chapter.create`'s `byStatus` block

Only `chapter.create` has a 5xx `byStatus` row. `image.upload.byStatus` is `{413,404}`, `outtake.create.byStatus` is `{404,413}`, and `project.create` and `snapshot.create` declare no `byStatus` at all — so for four of the five scopes the loop body never runs and both tests pass having asserted nothing.
- **Impact:** Scopes with no 5xx row do not escape the rule the test states; they fall through to `scope.fallback`, which the sweep never inspects. `snapshot.create.fallback` is "Unable to create snapshot. Separately, the new comment ("image.upload, the sibling non-idempotent scope, avoids the trap by carrying no 5xx rows at all") contradicts the pre-existing `byCode` comment about fifteen lines below in the same file, which records that without its entry "the 500 fell through to `uploadFailedGeneric`, which invites the retry that mints the duplicate row + blob F-12 exists to prevent." Carrying no 5xx rows is what routes a bare 500 to the retry-inviting fallback; the old comment is right and the new one is not.
- **Suggested fix:** Evaluate the arm a bare 5xx actually resolves to — `resolveError(new ApiRequestError("boom", status), entry).message` for 500/502/503/504 — rather than reading `byStatus` directly. It turns red today for `snapshot.create` and `image.upload`, which is the honest state.

### [I2] The branch's newly-committed record of the two-parser weakness omits the case reachable *with* locator agreement — the case that defeats the bomb gate
- **File:** `packages/server/src/backup/backup-zip-format.ts` (the new `findEocdOffset` doc comment); `paad/code-reviews/backlog.md` entry `3d5f0a91`; the new test name in `packages/server/src/backup/__tests__/backup-core.test.ts`
- **Bug:** jszip's `readEndOfCentral` computes `extraBytes = endOfCentralDirOffset - (centralDirOffset + centralDirSize)` and, when positive, sets `reader.zero = extraBytes` to handle prepended data. `walkCentralDirectory` applies no such adjustment — it reads the EOCD's central-directory offset as absolute. So on an archive with a prepended fake central directory, **both parsers locate the same EOCD** and then read **different central directories**. The Verifier reproduced this read-only: an archive with `smudge.db` (200,000 B) and `images/a.png` (100,000 B), size fields in the prefix rewritten to `1`, yields identical EOCD offsets, Smudge's parser reporting 1-byte entries, and jszip inflating the real 200,000 and 100,000 bytes.
- **Impact:** `checkDeclaredSizes(sizes, buf.length, limits)` is computed entirely from Smudge's side, so that archive validates three declared bytes and passes trivially; extraction then materialises the real entries via `file.async("nodebuffer")` — after step 7 has already moved the live data dir aside. The branch's three new records all describe the divergence as an EOCD-*locator* problem (the backlog entry's "Measured divergences: (a)(b)(c)" are all locator cases, and the doc comment closes with "keep this rule matching jszip's on every archive both can reach"). A future author following the entry's "collapse to one parser" plan sizes the work against an enumeration that omits the reachable case. CLAUDE.md's F-19 discipline makes the enumeration the mitigation.
- **Suggested fix:** Records only — the `findEocdOffset` revert was correct. Amend the doc comment and entry `3d5f0a91` to name the `extraBytes` / `reader.zero` divergence and state that it is reachable while the locators agree; drop the "matching jszip's rule on every archive both can reach" framing. Optional cheap interim guard before the single-parser rewrite: refuse any archive where `eocdOffset !== centralDirOffset + centralDirSize`, a shape `runBackup` never produces.
- **Confidence:** High (88)
- **Found by:** Security (`claude-opus-5[1m]`)

### [I3] The new `switchToView` latch makes Ctrl+Shift+Arrow announce "Could not navigate" for a navigation that succeeds, and makes the last chapter click lose
- **File:** `packages/client/src/pages/EditorPage.tsx` — the `viewSwitchInFlightRef` refusal branch at the top of `switchToView`; consumed by `handleSelectChapterWithFlush`; arbitrated by `navEpoch`/`settle` in `packages/client/src/hooks/useKeyboardShortcuts.ts`
- **Bug:** The arrow-key branch has no `e.repeat` check, so autorepeat produces overlapping presses, and `Editor.flushSave` returns immediately when not dirty — so the window opens only on a dirty editor, the case the latch was added for. Press 1 bumps `navEpoch` to 1, latches, and parks on `await editorRef.current?.flushSave()`. Press 2 bumps `navEpoch` to 2, hits the new latch, returns `false` through `handleSelectChapterWithFlush`, and its `settle(false)` passes the `myEpoch === navEpoch` test — announcing `STRINGS.sidebar.navigationFailed(title)`. Press 1's flush was never staled, so it completes and navigates, and its `settle(true)` is discarded as epoch-stale.
- **Impact:** The screen-reader user is told navigation failed while the app navigated — and because press 2 read `activeChapterRef` before press 1 moved it, the failure announcement names the very chapter the writer lands on, alongside a spurious `mutationBusy` banner. The `navEpoch` design comment states its premise explicitly ("press N+1 aborts press N's in-flight GET synchronously, so press N resolves false FIRST"); the latch inverts that premise for the `switchToView` leg. This re-opens the F-13/I1 defect the `settle()` design exists to prevent, on the one surface where the announcement is the user's only signal. Same root, second consequence: Sidebar, PreviewMode and DashboardView chapter clicks all route through `switchToView("editor")`, so clicking chapter C while chapter B's flush is in flight is now refused with a busy banner instead of superseding B. The new `EditorPageFeatures.test.tsx` case pins only the Ctrl+Shift+P double-press, which carries no announcement, so nothing catches either consequence.
- **Suggested fix:** Distinguish the re-entrancy refusal from a real navigation failure — a discriminated `switchToView` outcome, or `if (e.repeat) return;` in the arrow branch, or have the refusal await the in-flight switch and return its result.
- **Confidence:** Medium (75)
- **Found by:** Logic & Correctness, Contract & Integration, Concurrency & State (`claude-opus-5[1m]`)

### [I4] The latch is one-directional: every other guarded entry point can still cancel the view switch's in-flight flush
- **File:** `packages/client/src/pages/EditorPage.tsx` — `viewSwitchInFlightRef` is read only inside `switchToView`; `isActionBusy` is `mutation.isBusy() || actionBusyRef.current`
- **Bug:** `switchToView` sets neither `mutation.isBusy()` nor `actionBusyRef`, so `isActionBusy()` reads false for the whole flush window (seconds, in the 2s/4s/8s backoff ladder). Two classes of sibling entry point run freely in that window and sever the very PATCH the flush awaits. `handleCreateChapter` / `handleDeleteChapter` call `cancelInFlightSave()` (`saveSeq.abort()` + `saveOp.abort()`) at the top; the save loop returns `{kind:"aborted"}`, `flushSave` resolves `false`, and `switchToView` takes its `if (!flushed)` arm. The Ctrl+S `flushSave` callback reaches the same state by a different route.
- **Impact:** The writer sees `viewSwitchSaveFailed` ("your changes could not be saved") for a save their own click cancelled, the switch is abandoned, and the editor is re-enabled. The severe variant is "Replace all" in the still-open find-replace panel: `mutation.run()` calls `cancelPendingSaves()` and then its own synchronous `safeSetEditable(false)`; the abort makes the view switch's flush resolve `false`, and its `!flushed` arm then calls `safeSetEditable(editorRef, true)` — re-enabling the editor inside the mutation's committed window. Which lands last is pure task scheduling. If the continuation wins, keystrokes re-dirty the editor and the 1.5s debounce PATCHes pre-replace content over the committed replace — CLAUDE.md save-pipeline invariant 2, which the latch's own comment cites. The latch comment states the root cause correctly ("`switchToView` sets NEITHER") and then closes only the switch-vs-switch half.
- **Suggested fix:** Raise the shared `actionBusyRef` in `switchToView`, clearing it in the same `finally`, so the existing `isActionBusy()` gate covers the flush window in both directions — or record the residual beside the ref and file it, the way this branch filed `9c2ad4e1`.
- **Confidence:** Medium (74)
- **Found by:** Error Handling, Concurrency & State, Spec Compliance (`claude-opus-5[1m]`)

#### [OOSI2] Decompression-bomb ratio is computed against `buf.length`, so trailing padding dilutes it away — backlog id: `ebdb1c53`
- **File:** `packages/server/src/backup/backup-core.ts` — `runRestore` step 2, consuming `checkDeclaredSizes` in `backup-zip-format.ts`
- **Bug:** `checkDeclaredSizes(sizes, buf.length, limits)` tests `total / compressedTotal > maxRatio`, and `compressedTotal` is the whole file length rather than the sum of the entries' compressed sizes — `walkCentralDirectory` never reads CEN+20. Appending N bytes of padding after the EOCD, or a large archive comment, lowers the computed ratio without touching any entry.
- **Impact:** `maxRatio: 10` is bypassable — a 100 KB bomb padded to ~200 MiB clears the ratio arm entirely, leaving only `maxUncompressed` (2 GiB), and step 8 materialises each entry in RAM via `file.async("nodebuffer")` before writing. Trailing-byte tolerance is now a pinned, required capability (new test plus the `findEocdOffset` doc comment), which is what makes the padding free to add.
- **Suggested fix:** Sum the per-entry compressed sizes from the central directory (CEN+20, alongside the CEN+24 read already present) and pass that as `compressedTotal`; keep `buf.length` only as an upper sanity bound. Interacts with `3d5f0a91` — declared sizes are themselves forgeable while the two parsers disagree.
- **Confidence:** Medium (66)
- **Found by:** Error Handling (`claude-opus-5[1m]`)
