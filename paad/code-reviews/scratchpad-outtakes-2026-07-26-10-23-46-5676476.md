## Executive Summary

Phase 4c.2 (Scratchpad / Outtakes) is a well-built feature: no XSS, note-mark confidentiality holds, SQL is parameterized, the ProjectStore facade and wire contract are complete, and the documented invariants (hard delete, image-strip, exclusion by table separation) are implemented with real-SQLite tests. One **Critical** bug dominates: `OuttakesPanel` discards its entire list load whenever it mounts with a pending capture, so the drawer shows only the last captured row and hides every stored outtake for the rest of the session — found independently by five specialist lenses and reproduced empirically. Beyond that, five Important issues cluster around the same panel-state seam (a second load-discard path, an abort-a-committed-POST race, silent no-ops) plus a layout contract break; the remaining fourteen are one-liners and documentation/test-coverage gaps. Confidence is high — every surviving finding was re-verified against code at HEAD, three specialist claims were dropped as non-defects, and one was corrected.

## Critical Issues

### [C1] `OuttakesPanel` mounting with a non-null `capturedOuttake` discards its entire list load
- **File:** `packages/client/src/components/OuttakesPanel.tsx:61-86` (producer `packages/client/src/pages/EditorPage.tsx:472, 921, 1141`)
- **Bug:** Two effects run in declaration order on mount. Effect A (`:61`) calls `seq.start()` (epoch +1) and fires the list GET. Effect B (`:81`) then runs and — when `capturedOuttake` is non-null — calls `seq.abort()` (`useAbortableSequence.ts:36`, `counterRef.current += 1`) **synchronously on mount**, before the GET resolves. `token.isStale()` is then true, so `setOuttakes(rows)` at `:67` never runs. The list becomes exactly `[capturedOuttake]`. Effect B was written for the *update* case (superseding an in-flight reload) but fires unconditionally on mount, where the only thing it stales is the panel's own first and only load.
- **Impact:** The panel unmounts whenever the reference panel is closed (`EditorMainContent.tsx:383`) or another tab is selected (`ReferencePanel.tsx:118-127` renders only `activeTab.panel`). The persisted panel default is **closed** and the default tab is **images**, while the capture button lives in the always-visible header toolbar — so the primary flow (capture a selection, then open the Outtakes tab) lands squarely on this bug. `setCapturedOuttake` is never reset to `null`, and the load effect's deps are `[projectId, loadOp, seq]` (the latter two memo-stable), so there is **no other reload path**: every previously stashed outtake stays invisible until a full page refresh, and a later capture re-arms it. Two aggravated variants: delete the captured row, switch tabs and return → the deleted row is re-prepended as a ghost whose second delete 404s; switch projects without an `EditorPage` remount → project A's row leaks into project B's panel while B's real list is discarded. No data loss — the rows are safe on the server — but the drawer's core promise ("a safe, searchable home for cut text", design §1) is broken exactly after the action that populates it.
- **Suggested fix:** Seed a ref with `capturedOuttake?.id ?? null` at first render (a `useRef` initializer, so mount is a no-op) and skip the prepend effect when the id matches. On mount the server list already contains the captured row — it was POSTed before the panel mounted — so no prepend is needed. This also closes the cross-project variant. Add a regression test that mounts with a non-null `capturedOuttake` and asserts both the captured row *and* the server rows render; every existing test mounts with `capturedOuttake={null}` and only then rerenders, which is why the case is uncovered.
- **Confidence:** High
- **Found by:** Logic & Correctness (B), Error Handling & Edge Cases (B), Contract & Integration (B), Concurrency & State, Spec Compliance (`claude-opus-5[1m]`) — five independent discoveries, two with empirical repros

## Important Issues

### [I1] `stripImageNodes` / `toPlainText` walkers do not guard child shape — malformed JSON yields a 500, and an array-wrapped image survives the strip
- **File:** `packages/shared/src/tiptap-images.ts:3-5`, `packages/shared/src/tiptap-plaintext.ts:15-17`
- **Bug:** `TipTapDocSchema` (`schemas.ts:47-56`) types content as `z.array(z.record(z.unknown()))`, which constrains **top-level elements only** — nested `content[]` arrays are unvalidated (`.passthrough()`, and `validateTipTapDepth` only counts depth). The walkers dereference `node.type` with no shape guard. Verified by running the real modules: `{"type":"doc","content":[{"type":"paragraph","content":[null]}]}` passes `safeParse`, then `stripImageNodes` throws `Cannot read properties of null (reading 'type')` (as do `toPlainText` and `countWords`). Separately, `{"…content":[[{"type":"image",…}]]}` passes the schema and the **image survives the strip** — an array child has no `.content`, so `strip()` returns it verbatim.
- **Impact:** The throw escapes `createOuttake` uncaught → global handler → **500 `INTERNAL_ERROR` where the API contract says a malformed body is 400**. It also falsifies the doc-comment claim at `outtakes.service.ts:26-30` that the route is "the sole content-validation trust boundary" — the route's schema does not guarantee the shape the service's walker assumes. The array-child case falsifies a stronger claim: both `outtakes.service.ts:8-11` and CLAUDE.md §Data Model assert the strip keeps outtakes out of image-refcount paths **structurally**, but `extractImageIds` (`images.references.ts:63-69`) has the identical blind spot, so a surviving image id is invisible to the reaper and gets GC'd out from under the outtake. Reachable only via hand-crafted JSON (ProseMirror never emits null or array children) on a no-auth localhost app; the null-child crash class is already latent for chapters via `countWords`, but this branch **widens** it to two new walkers and a new endpoint and adds the array-child variant, which is new.
- **Suggested fix:** Guard the walker, not the caller: `if (!node || typeof node !== "object") return null;` (resp. bare `return`) at the top of each walk — one guard each covers every caller (outtake capture, chapter save, panel render). Mirror it in `extractImageIds` so the two sides of the reference count stay symmetric.
- **Confidence:** High
- **Found by:** Security, Error Handling & Edge Cases (A) (`claude-opus-5[1m]`)

### [I2] `OuttakesPanel` re-declares the ReferencePanel frame and hard-pins itself to 320px
- **File:** `packages/client/src/components/OuttakesPanel.tsx:140`
- **Bug:** Root element is `border-l border-border/60 bg-bg-sidebar flex flex-col h-full overflow-hidden w-80 min-w-80`. The owning `<aside>` (`ReferencePanel.tsx:42-46`) already supplies `border-l border-border/60 bg-bg-sidebar … overflow-hidden` and sets `style={{ width, minWidth }}` from the user-resizable 240–480px persisted value (`useReferencePanelState.ts:8-9`). The sibling tab, `ImageGallery.tsx:390`, is correctly just `flex flex-col h-full`.
- **Impact:** Below 320px `min-w-80` refuses to shrink; the tabpanel's `flex-1 overflow-y-auto` (`ReferencePanel.tsx:119`) computes `overflow-x` to `auto` per the CSS overflow spec, giving a spurious horizontal scrollbar, and the aside's `overflow-hidden` clips the spill — resizing appears not to work on this tab. Above 320px the content sits 320px wide inside a wider aside, leaving a dead gutter and a duplicate `border-l` drawn 0px from the aside's own border. Switching Images↔Outtakes at any non-default width visibly changes the layout of a panel the user just sized. The inner `flex-1 overflow-y-auto` also nests inside the tabpanel's own `overflow-y-auto`, yielding two scrollbars. Default width is 320px, so only users who resize hit it.
- **Suggested fix:** `className="flex flex-col h-full"`, matching the sibling.
- **Confidence:** High
- **Found by:** Contract & Integration (B), Logic & Correctness (B) (`claude-opus-5[1m]`)

### [I3] A mutation landing while the initial load is in flight permanently drops the loaded list
- **File:** `packages/client/src/components/OuttakesPanel.tsx:104` (also `:121`, `:127`)
- **Bug:** `handleCreate`'s success branch calls `seq.abort()` to protect its optimistic prepend. If the mount GET is still outstanding it is staled and discarded at `:66`. Interleaving: open the panel on a slow list GET → "New blank note" → type → Save → the POST resolves first → the GET's rows are thrown away. `handleDeleted` / `handleUpdated` cannot hit it today only because no cards exist before the load resolves.
- **Impact:** `outtakes` becomes `[newRow]` for the rest of the session, because the panel never refetches — the same end state as [C1] but from a different trigger, and **the fix for [C1] does not fix this**. The root problem is that `seq.abort()` is being used to *discard* a load whose result is still wanted, rather than to reconcile it.
- **Suggested fix:** Have the reconcilers bump a `reloadKey` that the load effect depends on, so a staled load is re-issued after the mutation commits (one extra GET in a rare race, and the refetch then reflects server truth). Alternatively, only `seq.abort()` when a load is known to be outstanding *and* schedule the refetch.
- **Confidence:** Medium
- **Found by:** Concurrency & State (`claude-opus-5[1m]`)

### [I4] A second toolbar capture aborts the first POST, which may already have committed
- **File:** `packages/client/src/pages/EditorPage.tsx:913-921`
- **Bug:** `captureOp.run()` aborts the prior controller (`useAbortableAsyncOperation.run`: `ref.current?.abort()`). If the first POST already reached the server the row is committed, but the client's `if (signal.aborted) return` fires, `mapApiError` maps ABORTED to `message: null`, and `setCapturedOuttake` is never called for it.
- **Impact:** A silently created outtake that never surfaces. Since the prepend is now the **only** thing that surfaces a capture (the reload path was removed in `d78e59c`), the row never appears — and per [C1] a panel remount will not show it either. The capture button gives no busy feedback (see [I5]), so a second click during a slow round-trip is the *expected* user reaction, not a rare race. Note this is not covered by CLAUDE.md's accepted trade-off F-8: that rationale rests on "there is no automatic retry path… the only route to a duplicate is a manual user retry", but here the abort is automatic.
- **Suggested fix:** Give capture a re-entrancy latch (ignore a second click while one is in flight, mirroring the panel's own `creating` flag) instead of aborting the prior POST. Abort-on-unmount stays via the hook. Aborting a POST that may have committed is the wrong cancellation semantic.
- **Confidence:** Medium
- **Found by:** Error Handling & Edge Cases (B), Concurrency & State (`claude-opus-5[1m]`)

### [I5] Insert and capture no-op silently with no user feedback, unlike their sibling entry points
- **File:** `packages/client/src/pages/EditorPage.tsx:481-489` (`handleInsertOuttake`), `:902-912` (`handleSendSelectionToOuttakes`)
- **Bug:** Three bare `return`s with no user-visible signal: (a) inserting a card while the editor is non-editable or the lock banner is up; (b) clicking the toolbar capture button with a collapsed cursor (`from === to`); (c) an image-only selection that strips to an empty doc. `EditorToolbar.tsx:190-220` renders the capture button with no `disabled` / `aria-disabled` tied to selection state.
- **Impact:** The user clicks a visible, enabled button and observes literally nothing. Case (b) is the everyday one. In the locked-editor case (a), telling the user why input is refused is the entire point of the lock banner. The established pattern in this same file is `onInsertImage` (`:1128-1138`), which surfaces `STRINGS.editor.mutationBusy` for exactly this "your click was intentionally ignored" situation.
- **Suggested fix:** Route (a) through `setActionInfo(STRINGS.editor.mutationBusy)` like `onInsertImage`; for (b)/(c) either disable/`aria-disable` the toolbar button when the selection is empty, or surface a short `actionInfo` string.
- **Confidence:** Medium
- **Found by:** Error Handling & Edge Cases (B) (`claude-opus-5[1m]`)
