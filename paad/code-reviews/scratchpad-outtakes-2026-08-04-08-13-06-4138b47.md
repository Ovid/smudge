## Important Issues

### [I1] Stale-closure project guard leaks project A's outtake into project B's panel
- **File:** `packages/client/src/components/OuttakesPanel.tsx:152` (reached from `:200`)
- **Bug:** `applyServerRow` is a `useCallback` with deps `[reconcile, projectId]`, but `handleCreate` is a plain async function body, so the running invocation pins the click-time `applyServerRow` — the one closed over project A's `projectId`. `createOp` (`useAbortableAsyncOperation`) aborts only on unmount and on a newer `run()`, never on a `projectId` prop change, and the panel is not unmounted across a project switch: `EditorMainContent.tsx:406` renders `<OuttakesPanel projectId={project.id}>` with no `key`, and `useProjectEditor.ts` only ever calls `setProject(data)`, never `setProject(null)`. So the guard compares A's `row.project_id` against A's captured `projectId`, passes, and prepends the row into what is now project B's list.
- **Impact:** Save a blank note in project A, navigate to B before the POST resolves, and A's outtake card renders in B's panel. Its **Insert** pastes A's private text into a B chapter; its **Delete** hard-deletes a real project-A outtake. Outtakes carry no `deleted_at` (CLAUDE.md §Data Model), so that is unrecoverable loss in a project the writer isn't looking at. This is precisely the harm the code's own comment at `:143-151` claims to have closed.
- **Suggested fix:** `const projectIdRef = useRef(projectId); projectIdRef.current = projectId;` and compare `row.project_id !== projectIdRef.current`. Fix together with [S2], which becomes reachable on the ordinary path once this lands. The existing test at `OuttakesPanel.test.tsx:288` cannot catch this — it stages a server-echoed wrong `project_id` with `projectId` held constant, so the closure is still current there.
- **Confidence:** High
- **Found by:** Logic & Correctness, Contract & Integration, Concurrency & State, Error Handling — all client partition (`general-purpose (claude-opus-5[1m])`). Security (client) assessed the same line as clean; the Verifier overruled that reading, having traced which `projectId` the closure holds.

### [I2] TipTap walkers guard the child shape but not the `content` container shape
- **File:** `packages/shared/src/tiptap-plaintext.ts:42` and `packages/shared/src/wordcount.ts:31-34`
- **Bug:** `TipTapDocSchema` types top-level elements only (`z.array(z.record(z.unknown()))`), and `validateTipTapDepth` ends with `if (!Array.isArray(content)) return true;` — so `{"type":"doc","content":[{"type":"paragraph","content":5}]}` passes validation. Both walkers then iterate `node.content` directly (`for (const child of node.content ?? [])`), throwing `TypeError: not iterable`. Every sibling walker in the corpus already guards the container: `stripImageNodes`, `stripNoteMarks`, `validateTipTapDepth`, `extractImageIds`, `collectLeafBlocks`, `splitBlockRuns`. These two are the only holdouts.
- **Impact:** Two reachable paths. `PATCH /api/chapters/:id` calls `countWords` at `chapters.service.ts:82` *before* the transaction → **500 `INTERNAL_ERROR`** where the contract says 400; nothing is written, and the writer's auto-save fails with "An unexpected error occurred". `POST /api/projects/:id/outtakes` returns **201 and persists the row** (`stripImageNodes` is array-guarded, so capture succeeds) — after which `OuttakeCard` calls both `toPlainText` and `countWords` on it, so the drawer throws on every render. Because the drawer renders the delete button, the row is not removable through the UI, and with no `ErrorBoundary` anywhere in `packages/client/src` the throw unmounts the whole React root. A persistent poison pill, not a transient error. The branch's own contract table (`tiptap-depth-walkers.test.ts:360-373`) enumerates `null`/string/number as *children* but never a non-array `content`, so the forcing test cannot see the gap — and `toPlainText` is absent from that block entirely.
- **Suggested fix:** `if (Array.isArray(node.content))` before the loop in `tiptap-plaintext.ts`; `if (!Array.isArray(node.content)) return "";` in `wordcount.ts`. Add a non-iterable-`content` row to the contract table and enrol `toPlainText` in it.
- **Confidence:** High
- **Found by:** Error Handling, Contract & Integration — both server/shared partition (`general-purpose (claude-opus-5[1m])`)
- **Classification note:** `wordcount.ts:31` is an untouched line, **promoted to in-scope** — the branch added a new caller (`OuttakeCard`) into the broken function and created the persistent-poison path. The Verifier kept both files as one finding rather than splitting, since splitting would let the `wordcount.ts` half be deferred as pre-existing and leave the poison-pill path half-fixed.

### Out-of-Scope Important

#### [OOSI1] `$`-sequences in an image caption splice the document into the export — backlog id: `1079f80c`
- **File:** `packages/server/src/export/image-resolver.ts:161-164`
- **Bug:** The figcaption pass is a *string* replacement interpolating `escapeHtml(fullCaption)`. `escapeHtml` neutralises `& < > " '` but not `$`, and it actively manufactures the hazard by rewriting `&` → `&amp;`, so the `$&` match token survives. `$1`, `` $` ``, `$'` and `$&` all substitute. `fullCaption` comes from `image.caption` / `source` / `license`, all user-settable via `PATCH /api/images/:id` with no character restrictions.
- **Impact:** Ordinary prose triggers it — a caption reading "Sold for US$1,200" splices the `<img>` tag back into its own `<figcaption>`. `` $` `` splices the entire preceding rendered document (title, TOC, prior chapters, the `<style>` block, since `renderHtml` runs `resolveImagesInHtml` over the whole document) into a figcaption meant to hold escaped text only — multiplicatively within one `.replace()` and compounding across images, so a 2000-char caption of `` $` `` tokens can turn a 1 MB export into ~660 MB and OOM the server. Affects HTML, Markdown, plaintext and EPUB; DOCX is unaffected.
- **Suggested fix:** Same shape as the sibling fix eight lines above — a function replacer: `(tag) => \`<figure>${tag}<figcaption>${escapeHtml(fullCaption)}</figcaption></figure>\``.
- **Confidence:** High
- **Found by:** Security — server/shared (`general-purpose (claude-opus-5[1m])`)
- **Backlog status:** re-seen (first logged 2026-07-26)
- **Classification note:** The anchor line is untouched and the figcaption block is byte-identical to `main`. The branch's `IMAGE_SRC_REGEX` widening does newly route *suffixed* srcs into the wrap, but no shipped path emits those, and the dominant trigger fired identically on `main`. Not promoted — consistent with the prior round's classification of the same finding.
